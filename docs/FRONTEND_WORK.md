# FRONTEND WORK — what `oriah-web` must do, phase by phase

**Status: live. Written 2026-11-09, at the end of Phase 0.** This is the
frontend half of [`MVP_PLAN.md`](MVP_PLAN.md). It lists every admin screen and
storefront change the plan implies, so the frontend stage follows the plan
instead of drifting from it. `CLIENT_DECISIONS.md` wins wherever this list and
the requirements disagree.

## How the frontend is built

**Backend first, then the frontend, from this list** (decided 2026-11-09;
`MVP_PLAN.md` Part 5 says the same).

1. Phases 1 to 13 are built in `oriah-api`. `oriah-web` is not changed while
   they are built.
2. **Each backend phase updates this list in the same commit.** Under its
   phase it records, for every change the frontend must follow: the exact
   endpoint, the request and the reply, the errors (problem types and
   statuses), the capability that may use it, and any browser test (Playwright
   spec under `oriah-web/e2e/`) the change breaks. An entry below that the
   phase settles differently is corrected, never left to contradict the code.
3. After Phase 13, the **frontend stage** builds this list in `oriah-web`,
   test-first, phase by phase in the same order, and regenerates the API
   types (`npm run codegen`). Phase 14 is after the MVP.
4. Every "settle" item below is a question for the phase that builds it. The
   backend phase answers it (or asks the owner) and writes the answer here.

**Why this order.** The money and stock rules live in the backend, and the
smoke test (`smoke-test.ps1`) is already the proof that the admin side works
end to end (`MVP_PLAN.md` Part 6). Screens built on a settled API are built
once. And nothing goes live until every phase is built (`CLIENT_DECISIONS.md`
§1.5), so a storefront that lags the backend for a while costs the business
nothing.

**What this means for the browser tests.** Between a backend phase and the
frontend stage, the screens and specs that phase lists under "What it breaks"
stay broken. That is expected and written down. **A failing spec that is not
on this list is a regression**, and is fixed at once.

## Phases 1 to 14

### Phase 1 — The event log convention

**Admin screens**

- **Payments list and summary: a new status, `CHARGING`.** Phase 1 made a card charge happen once per intent. An intent is `CHARGING` from the moment the charge is started until its outcome is known, and a payment whose answer never arrived is settled by payment's reconciler (it asks the gateway about intents stuck for 2 minutes, every 30 s). `GET /api/v1/admin/payments/summary` gains **`chargingCount`**: show it beside the other counts ("charging now"). A `CHARGING` row older than a few minutes means the reconciler cannot reach the gateway. **What oriah-web does with it today (checked): nothing fails, and nothing singles it out.** `AdminPaymentSchema.status` is a plain string and the screen prints the status text of every row, so a `CHARGING` row parses and is listed, but in the fallback colour; the filter in `src/components/admin/AdminPaymentsClient.tsx` (`STATUSES`) lists only the four old values, so it cannot be filtered for; `PaymentStatusSchema` in `src/lib/api/schemas/admin.ts` (the same four values) is used only by a null-tolerance test; and `AdminPaymentSummarySchema` is a plain `z.object`, which **silently drops `chargingCount`**. Because nothing breaks by itself, regenerating the API types will not reveal it. **Write the tests first, and make each one fail today:** (1) the status filter offers `CHARGING`, and choosing it asks the API for `status=CHARGING`; (2) a `CHARGING` row's badge carries the warning style, not the fallback `bg-stone-100`; (3) `AdminPaymentSummarySchema` keeps `chargingCount`, and the summary shows it. (A test that only supplies a page containing a `CHARGING` row passes already and proves nothing.) Then add `CHARGING` to `STATUSES`, to the badge colours (a warning colour) and to `PaymentStatusSchema`, and `chargingCount` to `AdminPaymentSummarySchema`. The generated `src/lib/api/generated/payment.ts` has neither: run `npm run codegen` in the frontend stage.
- Phase 1 itself (the outbox in each service that moves money, a processed_event inbox in each consumer, a relay that can replay) names no screen.
- Decide whether any screen reads this record. Assumption 17 asks that every movement of money and stock be 'recorded permanently, in order, with who and when'. Phase 1 builds the log and Phase 5 the reason-coded stock movements, but the plan names no screen that shows either, so nobody in the shop could look at the record.

**Storefront**

The outbox itself shows shoppers nothing, but the follow-ups Phase 1 fixed changed what checkout answers when payment goes wrong. The storefront must follow:

- **Superseded in Phase 7: confirm can no longer answer 502 (nothing is charged at checkout), so this bullet no longer applies; see Phase 7, Storefront, Confirm.** *As written in Phase 1:* **The 502 copy is now false and must change.** `POST /api/v1/checkout/confirm` answers **502** when the request to charge reached payment and no usable answer came back, so whether the card was charged is unknown. By then the order **is recorded** (status `CREATED`, unpaid) and the cart is left as it was. `src/lib/api/checkoutErrors.ts` (the `case 502`, around line 184) still says "Your order has not been placed. Check your order history before trying again" — untrue on both counts: the order exists, and the order list shows "Pending" whether or not the shopper was charged, so checking it cannot settle anything. New copy, in the shopper's words: *"Your order is recorded, but we could not confirm the payment, so we do not know whether your card was charged. Please do not pay again: your order shows as pending until we have checked. Contact us if you were charged."* `canRetry` stays `false` (a second confirm places a second order). The same text is the backend's `detail`. Update the test at `checkoutErrors.test.ts` (~line 73): it only looks for "order history", "support" or "do not", so pin the new meaning instead (recorded, do not pay again, contact us). `src/lib/api/generated/checkout.ts` (~line 310) still carries the old 502 description: regenerate it.
- **Superseded in Phase 7: a confirm that ends with no problem+json body is now safe to repeat.** If something between the browser and checkout cuts the confirm off (the proxy timeout below, a dropped connection), the storefront has no status of checkout's own and cannot know whether the order was placed. Phase 1 made that outcome non-retryable until MVP_PLAN Phase 7, gap 3 (one live order per cart) was closed, because a second confirm, sent under the new `Idempotency-Key` that a reload makes, would have placed a second order and a second charge attempt. Phase 7 closed that gap, and nothing is charged at checkout any more, so: repeat the confirm **with the same `Idempotency-Key`** and order hands back the order it already made; a new key for the same bag finds the live order by the quote's digest and answers it (200) instead of placing a second. If the bag is then empty (409 `cart-empty`), send the shopper to My orders. The Phase 1 copy that told the shopper not to pay again and to wait no longer applies; the wording to use is in Phase 7, Storefront, Confirm.
- **Superseded in Phase 7: a `503` from confirm no longer means that nothing was ordered, and there is no 502.** Phase 1 made `503` mean nothing was charged and kept 'outcome unknown' for 502. Since Phase 7 checkout touches no money: a `503` (with `Retry-After`) means a dependency did not answer and **the order may or may not have been placed**, and the answer to offer is 'Try again' with the same `Idempotency-Key` (Phase 7, Storefront, Confirm). The existing 503 copy, which says nothing was charged, must be reworded.
- **Must-do, still standing in Phase 7: the proxy timeout.** The Next.js rewrite proxy in front of checkout (Next 15.5.18) ends a request after **30 s** by default, and `oriah-web` sets none. Checkout can take longer: since Phase 7 it waits up to 20 s for order alone (order's placement makes five calls within a 15.5 s budget), after its own calls to cart, catalog, customer and shipping. The Phase 1 figures for this bullet (13 s to place the order, up to 22 s to create the payment intent, about 35 s before the card is charged) described a card flow that is gone. Either set the proxy timeout explicitly, above checkout's worst confirm, or give checkout an overall deadline: Phase 7 added no deadline inside checkout, so that choice (see Needs from the owner, below) is still open. Until it is made, repeating with the same key (the two bullets above) is what protects the shopper.
- **Superseded in Phase 7: `POST /api/v1/payments/intents` (create an intent) is off.** The card path is switched off unless `oriah.payment.card.enabled` is set (it is not, by default) and nothing calls it. The intent paths are removed from the published contract and answer 404, and the regenerated `generated/payment.ts` no longer has them. The contract this bullet gave in Phase 1 (200, 201, 400, 404, 409, 503 and 500, with the order checks) returns only when ZynlePay (Phase 13) gives the card path a caller.

**What it breaks in oriah-web today**

- **No Playwright spec** (`e2e/*.spec.ts`) depends on any of this: nothing matches on the old backend text, because the storefront ignores the 502 `detail` and shows its own copy.
- **A unit test passes by accident today:** `checkoutErrors.test.ts` (~line 73) accepts the old and any similar copy. It must be rewritten with the copy above or it will not notice the next wrong sentence.
- **Nothing will fail on its own for the admin payments screen**, which is the risk: a `CHARGING` row is accepted and listed without styling or a filter, and `chargingCount` is accepted and dropped (see above). The tests that would catch it do not exist yet; they are the first thing to write in the frontend stage, each written to fail first.
- The one trap the plan names is backend-only and held: the audit insert is not inside payment's post-charge transaction. The storefront's Idempotency-Key on confirm stays as it is.
- **An observation, not a break:** `e2e/storefront-happy-path.spec.ts` runs under Playwright's 30 s limit for the whole test. On 2026-11-10 its first run on a freshly started stack timed out waiting for "Place order" to become enabled (the button waits for the quote to settle). The same spec then passed alone (36.8 s of wall time) and in the full suite (6/6). It also leaves alice's item in her cart when it fails, so the next run sees a doubled bag (K 275.00, not K 137.50) and fails for that reason: clear her cart (`DELETE /api/v1/carts/me`) before re-running. In the frontend stage, raise this test's timeout and clear the cart in its setup.

### Phase 2 — Suppliers and the procurement service is born

**Admin screens**

- **New Suppliers screen**, gated on the `PROCUREMENT_ADMIN` capability (`OWNER` and `MANAGER` hold it; `SALES`, `DISPATCH` and `BOOKKEEPER` do not): list, add, edit, stop using, delete. New sidebar entry on the same capability. It starts empty ("Nothing is seeded").
- **The five calls**, all under `/api/v1/admin/procurement/suppliers`, through the gateway. Every error the service raises is `application/problem+json` with a `traceId` (show it to the person: it is what finds the request in the logs). A 401 or 403 refused at the gateway is also problem+json (type `unauthorized` / `forbidden`) but has **no `traceId`**, so the screen must not assume the field is there.

  | Screen action | Call | Success |
  |---|---|---|
  | Add | `POST /suppliers` | **201**, the supplier, and a `Location` header that is a relative path (`/api/v1/admin/procurement/suppliers/<id>`) |
  | List | `GET /suppliers?page=&size=&active=&q=` | **200**, a page (below) |
  | Open one | `GET /suppliers/{id}` | **200** |
  | Change, or Stop using | `PATCH /suppliers/{id}` | **200**, the supplier as it is now |
  | Delete | `DELETE /suppliers/{id}` | **204** |

  `operationId`s, for the generated types: `createSupplier`, `listSuppliers`, `getSupplier`, `updateSupplier`, `deleteSupplier`. The standard owner endpoint `GET /api/v1/admin/procurement/contact-info` (`fetchProcurementContactInfo`) is there too.
- **A supplier** has: `id`; `name` (required, at most 120 characters, **unique among live suppliers ignoring capitals**, and a stopped supplier still holds its name); `country` (required, an **ISO 3166-1 alpha-2 code** such as `ZM`, `CN`, `AE`: build a **country picker**, not a text box, because "Zambia" or "UK" is a 400; stored in upper case); `contactName` (optional, at most 120); `contactDetails` (optional, at most 500: phone, WhatsApp, email); `paymentNotes` (optional, at most 500: "how you pay them", **in words**); `active`; `version`; and `createdAt`, `updatedAt`, `createdBy`, `updatedBy`. The three optional fields come back as `null` when empty. The name and the notes are trimmed; the text may not contain the NUL character (a 400 with `fieldErrors`; a form never produces one).
- **The list** answers a Spring page: `content`, `totalElements`, `totalPages`, `number`, `size`. It is **always ordered by name ignoring capitals** (then id): the caller cannot choose an order, and asking with `sort` is a 400, not ignored. `size` is 1 to 100 (default 50); a `size` outside that, a negative `page`, or a `page` so far in that its offset overflows is a **400** (`bad-request`), never quietly clamped. `q` finds names **containing** the text, ignoring capitals (`%` and `_` are ordinary characters). **With no `active` filter, stopped suppliers are listed too**: either default the screen to `active=true` with a "show stopped" switch, or mark stopped rows plainly. A deleted supplier is never listed.
- **Change (`PATCH`): send only what changed, and always send `version`.**
  - A field **left out** is unchanged. `contactName`, `contactDetails` and `paymentNotes` are **cleared** by sending `null` or blank text. `name`, `country` and `active` can be replaced but **never emptied** (a 400 with `fieldErrors`); `"active": null` is a 400 too.
  - **`version` is the `version` of the supplier the form was loaded with.** If someone else saved it since, the change is refused with **409 `concurrent-update`** and nothing is applied, even if the two edits touched different fields: reload, show the new values, and let the person do it again. This is what stops a form left open for an hour from overwriting a colleague's change to how Oriah pays a supplier. A `version` of `null`, or not a number, is a 400. Leaving `version` out skips the check (the last save wins): do that only on purpose.
  - Sending back the whole supplier from the last read is safe: fields the API does not have (`id`, the audit fields) are ignored. **`version` is strict**: it must be a whole JSON number of 0 or more (a quoted `"5"`, `5.5`, `-1`, `true` and `null` are all 400). The other fields are read leniently by the platform's JSON reader (it will turn `"5"` into text or `1` into true rather than refuse it), so do not rely on that: send `active` as a real boolean and the text fields as strings.
  - **"Stop using"** is `{"version": n, "active": false}`; "Use again" is `active: true`. It means a real supplier Oriah no longer buys from (from Phase 4 it gets no new purchase orders); it is not a deletion and its name stays taken.
- **Delete is for correcting a mistake**, a supplier added by error. It frees the name, and the supplier is gone from every screen (a second delete is a 404). The screen must say so in its words: **"Stop using"** for a supplier Oriah is finished with, **"Delete (added by mistake)"** for a record that should not exist. A Delete button must never be the way to stop buying from someone.
- **Errors to handle on the add and change forms:** **400 `validation`** with `fieldErrors` (`[{field, message}]`, one per field at fault, all at once): attach each to its input; add and change use the same shape, so one form component serves both. **409 `conflict`**: the name is taken (ignoring capitals) by another live supplier. The `detail` usually reads "A supplier named '<the name you sent, trimmed>' already exists"; in a simultaneous-save race it is the generic "A supplier with this name already exists." Do not match on the text: show your own copy beside the name field. **409 `concurrent-update`** (above). **404** (it was deleted, or never existed). **403** (no capability) and **401** (signed out). A malformed id in the URL is a 400.
- 'How you pay them' is a **description on the supplier, not a payment record.** Supplier deposits and part-payments are ruled out (§6, Q1), and what was paid is each consignment line's all-in bank total (Phase 4). Build no supplier-payments ledger. The invoice is the Phase 4 upload. Label the field "How you pay them (notes)".
- **Settled 2026-11-10: there is no packaging screen in this phase.** The plan's Phase 2 line used to say 'packaging types'; packaging is a **catalog** entry of kind = PACKAGING (Phase 3), so it is built there and shown on the catalog screens. Phase 2's Suppliers screen is suppliers only.

- None. Suppliers are back-office.

**What it breaks in oriah-web today**

- No current screen or spec breaks, because this is a new service on a new path. `oriah-web/scripts/codegen.mjs` has no procurement entry yet (see cross-cutting): add `procurement` (its spec is served at `/v3/api-docs/procurement` through the gateway) and run `npm run codegen`. In the generated `UpdateSupplierRequest`, `contactName`, `contactDetails` and `paymentNotes` are `string | null` (that is how they are cleared) and `name`, `country`, `active` and `version` are not nullable: keep it so.

Uploading several photographs at once is safe but gains nothing: send them one after another. A 201 is unchanged. **A very large picture is slow to process**: the largest accepted (8000 x 5000, turned upright from a sideways phone photograph) took 166 s on the slow test PC, and the storefront's 30 s proxy limit would cut it off. Show the upload as "working" for as long as the request is open, tell the person to try a smaller export when it times out, and do not retry a timed-out upload on your own (the server may still finish it, and a repeat of the same bytes returns the first image).

### Phase 3 — Catalog holds packaging; the product exists before the stock

> **Built 2026-11-12 — what the API does now (the bullets below it are the screens that use it).**
>
> - **`kind` on a product.** `POST /api/v1/admin/products` takes an optional `kind`: `SELLABLE` (the default, so today's dialog still works) or `PACKAGING`. It is **fixed for life**: a `PATCH` that names a different `kind` is a 400 (naming the same one, or none, is fine). Every product response now carries `kind` (the public ones too, always `SELLABLE`).
> - **A packaging entry is typed `PACKAGING`**, with no spec fields: sending `productType` as anything else is a 400, sending `PACKAGING` for something sellable is a 400, and so is changing the type across that line. `GET /api/v1/product-types` now lists a third type, `PACKAGING`: **the type picker must not offer it** for a sellable product (and must not offer the others for packaging). Hide the whole spec section for packaging.
> - **Packaging is never published and never priced.** `POST .../publish` on it is a **409** whose `detail` says it is packaging: hide the Publish button. Its variants are created and kept at **`unitPrice` 0.00** (the field is still required: send `0.00`); any price above zero, on create or on a reprice, is a 400. Hide the price field and the pricing screen for it.
> - **More than one variant now works.** `optionNames` (for example `["Ring Size"]`, `["Strap", "Case Size"]`) is accepted on create and on `PATCH`, and every product detail and admin read returns it. **Declare the axes before adding variants:** each variant's `options` must have exactly those keys (`{"Ring Size": "M"}`), and two variants may not share a combination. Until now nothing in the API could set the axes, so a product could hold only one variant with no options. A `PATCH` that changes the axes is a 400 naming the active variant it would strand, and **today nothing in the API can edit a variant's options or switch a variant off** (only add and reprice), so the axes can be changed only while the product has **no** variant: to give a product that already has one different axes, create a new product (the screen should say so rather than offer a way out that does not exist). A null, blank or repeated axis name is a 400. Names are trimmed but **not** case-folded: `Size` and `size` are different axes. Packaging in sizes is one entry with a variant per size.
> - **The operator's list: `GET /api/v1/admin/products`** (`CATALOG_ADMIN`; operationId `listForAdmin`). Query parameters: `kind` (`SELLABLE` | `PACKAGING`), `status` (`DRAFT` | `ACTIVE` | `ARCHIVED`; **offer `DRAFT` and `ACTIVE` only**: `ARCHIVED` is set only when a product is deleted, and a deleted product is never listed, so that filter always returns an empty page), `q` (plain text, case-insensitive, matched against the **title and every variant's SKU**; a `%` or `_` typed in it means that character), `page` (from 0), `size` (default 20, **at most 100**). Newest first. Reply: the usual page envelope (`content`, `page`, `size`, `totalElements`, `totalPages`) of the admin product, **variants included**, so it is also the picker for consignment lines (Phase 4). It shows drafts and packaging and never shows a deleted product. A kind or status that does not exist is a 400. Use it for the Products table and for the dashboard's Catalogue count (the public list leaves drafts and packaging out).
> - **`201 Location` on create now points at the admin read** (`/api/v1/admin/products/{id}`), because a new product is a draft and the public read 404s it. Anything that followed the old `Location` was following a URL that could not return the new product.
> - **A shopper can never reach packaging**: the public list and `GET /api/v1/products/{id}` leave it out (404), and `POST /api/v1/variants/pricing` answers `UNKNOWN` for a packaging variant, with no id and no title, so a bag can never hold one.
> - **Search** lists only products that are published **and** sellable: a draft, an archived product and packaging never come back. The storefront has no search box, so nothing changes on screen.

### Phase 4 — Procure: purchase orders and consignments

> **Built 2026-11-12 — what the API does now (the bullets below it are the screens that use it).** Everything is under `/api/v1/admin/procurement/`, through the gateway, and needs `PROCUREMENT_ADMIN` (cost and allocation reads too: decided while building, with no `COST_VIEWER` check; see the cost-hiding bullet below). Every error is `application/problem+json`; a refusal made by the service carries a `traceId`. **Every change to an existing purchase order or consignment names the version it was made from** (`version` in the body, or `?version=` on the two DELETEs): a stale one is **409 `concurrent-update`**, a missing one a 400. Creating an order or a consignment sends none (a consignment made from orders carries each order's `version`), and neither does uploading or voiding a document. Money is a JSON number to the ngwee (`6000.00`); a finer amount is a 400 with `fieldErrors`. Money is always `ZMW`. **A count, a version and a weight in grams are whole numbers: a fraction (`"quantity": 1.9`, `"version": 0.5`) is a 400, never rounded**, so send them as integers (a form's number input does; build them from `Number(...)` and never from a division). A variant's label can be long (over 600 characters with several option axes): never size a column or a cell to 300.
>
> **The purchase order is its own record** (the open question below is settled): what Oriah placed with ONE supplier, `PO-000123`. `POST /purchase-orders` (`createPurchaseOrder`, 201 + relative `Location`), `GET /purchase-orders?supplierId=&status=&page=&size=` (`listPurchaseOrders`, newest first; `sort` is a 400), `GET /purchase-orders/{id}` (`getPurchaseOrder`), `PATCH /purchase-orders/{id}` (`updatePurchaseOrder`: `version` plus any of `placedOn`, `note`, `lines`; `lines`, when sent, REPLACES all of them), `POST /purchase-orders/{id}/cancel` (`cancelPurchaseOrder`, `{version}`). One to 100 lines; a line is `{variantId, quantity (1..1,000,000), totalPaid}`: **`totalPaid` is the all-in total as the bank app shows it. There is no unit price and no bank-charge field.** Label it "Total paid, as the bank app shows it". Every variant is checked with the catalogue once, here: a variant that does not exist, is switched off, or belongs to a deleted or archived product is a **400 `fieldErrors` naming `lines[i].variantId`** (a DRAFT product and packaging are fine). The catalogue being unreachable is **503 with `Retry-After`** and nothing saved: retry, as for photographs. The names (`sku`, `productTitle`, `variantTitle`, `kind`) are copied onto the line when it is placed, so history does not change when a product is renamed. **A supplier that has been stopped gets no new order (409)**; **a supplier any order names cannot be deleted (409, "stop using it instead")** (the delete button on a supplier with orders must explain, not just fail). An order that is in a consignment is **frozen**: `PATCH` and `cancel` are 409 until it is taken out.
>
> **A consignment is one shipment, built from WHOLE purchase orders** (no part-shipments, no short or extra deliveries). `POST /consignments` (`createConsignment`, 201): either `{"purchaseOrders":[{"id","version"}...], "note"}` (1 to 20 orders; **send each order's `version` as it was read**, a stale one is 409) or `{"opening":true, "lines":[{"variantId","quantity","totalCost", optional "chargeableWeightGrams","originCountry","hsCode"}...]}` for the **opening consignment** (day-one stock: no supplier, no order, always an estimate, **a K0 `totalCost` is a 400**, 1 to 200 lines, one line per variant, the variants checked with the catalogue like an order's). Reads: `GET /consignments?status=DRAFT|RECEIVED&opening=true|false&page=&size=` (`listConsignments`, newest first, a summary per row with `orderCount`, `lineCount`, `goodsTotal`) and `GET /consignments/{id}` (`getConsignment`: the header, the orders, the lines, the cost lines, the totals). `reference` is `C-000045`. A line copied from an order says which order and which **supplier** (`supplier` and `purchaseOrder` are `null` on an opening line: show "Opening stock / supplier unknown"); the same variant from two suppliers is two lines, because cost belongs to a receipt.
>
> **The draft is edited with:** `PUT /consignments/{id}` (`updateConsignmentHeader`: the **whole header is replaced**, so send every field you want kept: `note`, `chargesBasis` `DUTY_PAID|FREIGHT_ONLY` with **no default**, `declarant`, `clearanceForm` `CE6|CE20`, `zraAssessmentRef`, `licensedAgentUsed`; a blank or absent one is cleared. **`estimated` is the exception: left out, it keeps its value**; the opening consignment cannot be saved as "not an estimate" (400)); `PUT /consignments/{id}/lines/{lineId}` (`updateConsignmentLine`: `chargeableWeightGrams` for the WHOLE line in whole grams, `originCountry` two letters, `hsCode` digits and dots; replaced as a whole); `PUT /consignments/{id}/opening-lines` (`replaceOpeningLines`: the opening stock as a set); `PUT /consignments/{id}/cost-lines` (`replaceCostLines`: **every cost line as a set**, an empty list clears them); `POST /consignments/{id}/purchase-orders` (`attachPurchaseOrder`: `{version, purchaseOrderId, purchaseOrderVersion}`); `DELETE /consignments/{id}/purchase-orders/{orderId}?version=` (`detachPurchaseOrder`: frees the order and drops what was typed for its lines); `DELETE /consignments/{id}?version=` (`deleteConsignment`, 204: a draft only, with its lines and costs; its orders are freed). Each answers the whole consignment (200), except the delete.
>
> **Cost lines.** `{costType, amount, basis?, treatment?, incurredOn?, note?, shares?}`. `costType` is a **closed list**: `COURIER_INBOUND` (the courier's one charge, "keyed as billed"), `FREIGHT`, `INSURANCE`, `PORT_INCIDENTALS`, `INBOUND_TRANSPORT`, `AGENT_FEE`, `DUTY`, `SURTAX`, `IMPORT_VAT`. **A bank or transfer charge is refused** (400 naming `costLines[i].costType`, with the reason in plain words: the supplier price already is the total that left the bank), so the picker offers none. `basis` (`UNITS` `VALUE` `WEIGHT` `DIRECT`) defaults by type: courier, freight and inbound transport `UNITS`, agent fee `VALUE`, **duty, surtax and import VAT `DIRECT` only** (typed per line, never pooled; a 400 otherwise); `INSURANCE` and `PORT_INCIDENTALS` have no default, so the form must ask. `treatment` is `CAPITALIZE` (the default: rides on the goods into the unit costs) or `PERIOD` (a bill for the month: shown here, left out of the unit costs, **not shared and cannot carry `shares`**). Zero amounts are allowed (duty reads zero today; keep the lines, collapsed). **`shares`** is the person-typed split: one `{lineId, amount}` for EVERY line, adding up to `amount` exactly (the 400 says by how much it is out; who typed it is recorded, `typedBy` / `typedAt`). It is **required in effect for a `DIRECT` cost above zero** (a `DIRECT` cost of zero needs none) and an optional override for any other basis: this is the "editable distribution", typed as each line's total share of the cost, never a per-unit figure; the unit-level split inside each line is still done by the allocator. **`DUTY_PAID`** says the courier's price already includes duty, so a duty, surtax or import-VAT line above zero is a 400, and setting `DUTY_PAID` while one is above zero is a 400 too.
>
> **The allocation.** `GET /consignments/{id}/allocation` (`previewAllocation`) is what each unit costs, worked out by the server (never in the browser): per line `goodsTotal`, `sharedCost`, `landedTotal` and `slices` (at most two unit costs, a ngwee apart, **dearer first**: `4 x K1,528.99` and `3 x K1,528.98`); per cost what it put on each line (`perLine`, empty for a `PERIOD` cost); and the totals. **A consignment that cannot be costed yet is not an error**: `ready:false`, `lines` empty, and `problems` lists in plain words what to fix, each naming the cost line or line (a cost shared by weight with a line that has no weight; a `DIRECT` amount nobody typed; a typed split that no longer covers the lines because an order was attached or taken out). **Call it before Receive and show `problems`; do not parse the 409 text.** For a RECEIVED consignment it returns the allocation **recorded when the goods landed** (`revision`, `receivedAt`), never recomputed.
>
> **Receive.** `POST /consignments/{id}/receive` (`receiveConsignment`, `{version}`) works the allocation out, records it for good (revision 1), makes the consignment and every order in it `RECEIVED`, and announces each line (`consignment.received`) for inventory: all or nothing. **409** when the version is stale, it is already received, it cannot be costed yet (the `detail` repeats the problems), or **it is the opening stock and a shipment has already been received** (opening stock must come first: oldest-first selling depends on receipt order). Afterwards **every change is 409**, including `DELETE` ("history"): the screen goes read-only. A correction is the Phase 5 amendment. `receivedAt` is the server's time, not typed: there is no back-dating.
>
> **Invoices are stored by procurement itself, not in SeaweedFS** (the Phase 4 text below says SeaweedFS; this overrides it): a handful a month, and a document in the same database as the thing it supports cannot be orphaned. `POST /consignments/{id}/documents` and `POST /purchase-orders/{id}/documents` (`uploadConsignmentDocument`, `uploadPurchaseOrderDocument`; **multipart** with parts `file` and `kind` and optional `note`; `kind` is `SUPPLIER_INVOICE`, `COURIER_INVOICE`, `ZRA_ASSESSMENT` or `OTHER`; an order takes only `SUPPLIER_INVOICE` and `OTHER`). **A PDF, JPEG or PNG, 5 MB at most**: the type is read from the file itself, so a program renamed `.pdf` is a 400 whatever the browser claimed; say "PDF, JPEG or PNG, up to 5 MB" beside the picker, and **check the size in the browser first**: the server refuses a file over 5 MB with **413** before it reads it (its message is generic, so show your own "that file is over 5 MB: scan or save it smaller"). Let the browser set the multipart boundary itself (`fetch` with a `FormData` body and no `Content-Type` header): a hand-set `Content-Type: multipart/form-data` drops it and is a 400. A 201 carries `id`, `filename` (tidied, with an extension that fits), `contentType`, `sizeBytes`, `sha256`, `uploadedBy`. The same file twice on one owner is **409**; **10** in use at most per owner (409). **Only two uploads are taken in at once** (a 5 MB file is held in memory about three times over while it is read): a third waits up to 20 s for a place, and if none comes it is **503 with `Retry-After: 5`** and nothing is stored, so **retry after the header's seconds** (once or twice, then say "the server is busy with other uploads, try again in a moment") rather than show a failure; one person uploading one invoice at a time never sees it. `GET .../documents?includeVoided=` lists them; `GET /documents/{id}/content` (`downloadDocument`) is **always an attachment**: link to it, never embed it in an iframe or `<img>` (it is served with a policy that lets it do nothing). **There is no delete and no replace**: `POST /documents/{id}/void` (`voidDocument`, `{reason}` required) marks a mistaken one, which stays on record with who, when and why; upload the right one as a new document. A **received consignment still takes documents** (the courier's invoice often arrives after the goods). Deleting a draft consignment takes its documents with it; an order's documents stay.
>
> **Breaks in `oriah-web`:** none (new screens, new paths). Regenerate the procurement types (`npm run codegen`; the spec is `/v3/api-docs/procurement`). In the generated types the nullable fields are `string | null` (a consignment's `note`, `chargesBasis`, `declarant`, `clearanceForm`, `zraAssessmentRef`, `receivedAt`; a line's `productTitle`, `originCountry`, `hsCode`; a cost line's `incurredOn`, `note`, `typedBy`, `typedAt`; a purchase order's `note` and `consignmentId`; a document's `note`, `uploadedBy`, `voidedAt`, `voidedBy`, `voidReason`), `boolean | null` (`licensedAgentUsed`), `number | null` (a line's `chargeableWeightGrams`; the allocation's `revision`) and `object | null` (a line's `supplier` and `purchaseOrder`): keep it so. The storefront's 30 s proxy limit is not a concern here (the slowest call is receiving a consignment, which holds at most 200 lines).
>
> **What was built differently from the stub below, and why.** (1) *"the person who overrode it is recorded":* **built** (CLIENT_DECISIONS 3.3: every override records the actor). A cost line whose split a person typed carries `typedBy` (their Keycloak subject) and `typedAt`, on the consignment (`costLines[]`) and in the allocation (`costs[]`, beside `typed`); both are `null` when the allocator shared the cost. Show it beside the sum ("typed by <name>, <time>"; resolve the subject to a name the way the other screens do). It stays the FIRST typist's when someone else saves the list again with that split unchanged, and becomes the changer's when the split changes; it is kept in the recorded allocation inputs too. A typed split nobody is recorded as typing cannot be received (not reachable through the API). (2) *Basis defaults "UNITS (WEIGHT where a weight is recorded)":* the server does not switch basis by itself; the person chooses `WEIGHT` per cost, and the allocation says which line lacks a weight. (3) *The invoices are not in SeaweedFS* (above). (4) *"may a consignment take a switched-off variant or one on an archived product":* **no**, checked when an order line (or opening line) is placed; nothing is re-checked at receive, so goods already ordered and paid for are never stranded by a later archive.
>
> **Open questions for the owner** (defaults chosen; none blocks): (a) Oldest-first selling follows the order consignments are RECEIVED in, so staff must receive shipments in the order they arrived. (b) A piece missed from the opening count after a shipment has been received is entered as a normal consignment (opening stock cannot be received late). (c) Goods bought and carried home without a forwarder (no courier charge): enter a consignment with no cost lines; there is no third "charges basis" value for it. (d) Which month owns a `PERIOD` cost: the receipt date, unless `incurredOn` is given. (e) May there be more than one opening consignment? The build allows several, so long as no shipment has been received. (f) A shipment may be received with its charges basis left blank (it is recorded when known, with no default, and matters only when a duty line is keyed): should receiving REQUIRE it for a shipment?

> countMismatches[], ledgerMismatches[], commitmentMismatches[], reservedMismatches[]}` (the third came with Phase 6, the fourth with Phase 7); **all four lists empty means every count equals its lots, every lot equals its ledger, every box's set-aside count equals its products' records and every reserved count equals the lines of the holds in force**. Anything in
> them is a bug to report, not something a person fixes; a small "stock checks out" indicator on the Inventory page is enough, **green only when all four lists are empty** (one built from the first two alone would ignore the set-aside and reserved checks). A `commitmentMismatches` row is `{variantId, committed, sumOfCommitments}`: a box's set-aside count differs from its products' records (each record's `quantity` less its `held`). A `reservedMismatches` row is `{variantId, reserved, sumOfHeldLines}`: a stock row's reserved count differs from the sum of the lines of the holds in force.
>
> **Correcting a received consignment — `PROCUREMENT_ADMIN`** (all under `/api/v1/admin/procurement/consignments/{id}`). The consignment is never
> edited; a correction is a new **revision** of its allocation. `GET {id}` now carries **`revision`** (null on a draft; 1 as received; higher after a
> correction) and, once corrected, its lines' `goodsTotal`, its `costLines` and `estimated` **are the latest revision's** (the `version` stays the one
> from receipt: do not use it for a correction). **The list (`GET /consignments`) follows the correction too**: each row carries `revision`, and the goods total and `estimated` that stand. `POST {id}/amendments` (`amendConsignment`): `{fromRevision, reason, costLines?, goodsLines?,
> estimated?}`. **Say only what changes:** `costLines`, when sent, **replaces the whole cost list** (the same rules and the same `CostLineRequest` as a
> draft: send the courier's charge again with the new amount, and every other cost you want kept; no bank charge; duty only per line; a typed split
> names every line and adds up); `goodsLines` is `[{lineId, goodsTotal}]` for the lines whose all-in total was mistyped (above zero; the purchase order
> and its invoice keep what was typed, only the cost follows); `estimated` clears a shipment's "approximate" flag (**the opening stock stays an estimate
> for good: false is a 400**). **`fromRevision` is the revision the person was looking at**: someone else's correction since is **409
> `concurrent-update`** (reload and show the new figures); a draft is 409; **a correction that changes nothing is 400**; a missing `reason` (up to 200)
> or `fromRevision` is a 400 with `fieldErrors`. **201**, a relative `Location` (`.../allocation?revision=2`) and `{revision, reason, amendedBy,
> amendedAt, estimated, allocation, recutLines}`: `allocation` is the corrected allocation exactly as `GET .../allocation` shows it, and
> **`recutLines` are the lines whose cost changed** (inventory is told about those and only those; the others are untouched). `GET
> {id}/revisions` (`listConsignmentRevisions`): every revision, oldest first, with `reason` (null for the receipt), `createdBy` (the person's id:
> resolve it to a name as elsewhere), `createdAt`, `estimated`, the totals and `changedLines`. `GET {id}/allocation?revision=n` reads any one
> revision (404 for one that does not exist); left out, the revision that stands. **The screen shows the original beside the correction and says that
> every month whose sales, write-offs or give-aways used those units is corrected** (inventory does it, usually within seconds; the Costs screen shows the
> replaced lots and ledger rows, `live: false`, and the new ones with the higher `revision`).
>
> **Storefront.** `GET /api/v1/products/{id}` (the product page): **each variant now carries its own `availability`** (`IN_STOCK`, `LOW_STOCK` for under
> 5, `OUT_OF_STOCK`, `UNKNOWN`), and the product's `availability` is the variants' **together**. A variant that was never received, or is sold out,
> is `OUT_OF_STOCK` (not `UNKNOWN`); `UNKNOWN` means the stock service could not be asked. A withdrawn or unpriced variant has none (null). The product list and the admin product LIST still carry none; the admin single-product read (`GET /api/v1/admin/products/{id}`) carries the same badges as the public page (it asks inventory once per size, so do not call it in a loop).

> **Breaks in `oriah-web`:** the Inventory page's seed form (`seedInventory`, `POST /v1/admin/inventory`) calls a retired path, and nothing may call
> `confirm` through the gateway; no Playwright spec seeds inventory, so none breaks (checked). Nothing else changes shape: `VariantResponse.availability`
> is the field that already existed (it was always null on this read before).

Keep on hand, reserved and available. 'One count, not three' means on_hand is the only stock count in the system: catalog keeps none, procurement records only what was received, and the sum of the lots' qty_remaining must equal on_hand. It does not mean reserved disappears from the screen.

### Phase 6 — Price and publish

> **Status: the API is built (2026-11-13). The screens are not.** Everything below is the API **as built**, from the code and its tests,
> not from the plan. Money is ZMW to the ngwee throughout.

**The order in the real world, and what the screens must follow:** create the product and its variants (no price) → record and receive
the consignment → **price** → optionally choose the default box (and set boxes aside) → **publish**. A variant is created **unpriced**
(`unitPrice` 0.00). The only way it gets a price is the pricing endpoint below.

**Admin screens**

- **Pricing screen** — needs **both CATALOG_ADMIN and COST_VIEWER** (OWNER and MANAGER hold both; BOOKKEEPER sees cost but may not price; SALES neither). The gateway and the service refuse either alone (403), so hide the screen unless the person holds both (`oriah-web/src/lib/auth/capabilities.ts`).
  - **Read** `GET /api/v1/admin/pricing/variants/{variantId}[?targetProfitPercent=40]` returns `currentPrice` (null when unpriced; has `id`, `unitPrice`, `effectiveFrom`, `recordedAt`, `setBy`, `setByName`, `source` SET|MIGRATED, `assessment`, `reason`, `costBasis`), `assessment` of that price **against the cost now** (`OK`, `BELOW`, `NO_COST_KNOWN`, `CURRENCY_MISMATCH`; null when unpriced) and `shortfall`, `cost` (`floor`, `goodsHighest`, `boxHighest`, `boxBasis` NONE|NO_HELD_STOCK|COUNTED, `estimated`, `evaluatedAt`, and `goods` / `box` each with `lots[]` — `unitCost`, `qtyRemaining`, `estimated`, `revision`, `consignmentReference`, `receivedAt` — plus `highestUnitCost` and `averageUnitCost`, "shown beside it, never compared with"), `suggestion` (`targetProfitPercent`, `landedCost`, `suggestedPrice`; null when no percentage is asked or configured or no cost is known), `history[]` newest first, and `defaultPackagingVariantId`. A packaging variant is 409 `packaging-is-not-priced`. **Amended in Phase 7:** the answer also carries `discountPerPiece`, `promotionId` and `netPrice` (`discountPerPiece` is K0.00 and `promotionId` null when no promotion applies, and `netPrice` is then the list price; all three are null for an unpriced piece), and `assessment` and `shortfall` are judged on `netPrice`, the list price less the promotion in force, not on `currentPrice.unitPrice` (see Phase 7, Promotions screen rebuilt).
  - **Save** `PUT /api/v1/admin/pricing/variants/{variantId}/price` with `{unitPrice, currency?, effectiveFrom?, belowCostReason?, acknowledgedFloor?, expectedPriceId}`. `expectedPriceId` is **required in the sense that it must be right**: send the `currentPrice.id` the person saw, or `null` if they saw it unpriced; a price saved in between is 409 `stale-price` (reload). Currency is ZMW only (omit it; any other is 400 `unsupported-currency`). Answer: `price` (the new history row), `assessment`, `cost`, `productStatus`, `publishable`. **Amended in Phase 7:** the answer also carries `discountPerPiece`, `promotionId` and `netPrice`, and `assessment` is judged on `netPrice`.
  - **The warning never refuses, but it is a two-step flow.** A price below the dearest held cost (plus the default box's) first answers **409 `below-landed-cost`** carrying `floor`, `shortfall`, `assessment`, `estimated` and `cost` (every lot, the average). The screen shows them and asks for a **reason (5 to 200 characters)**; the second call repeats the same body with `belowCostReason` and `acknowledgedFloor` = the `floor` the person saw. If the floor has risen in between, the warning comes back again with the new figures (a reason is never accepted against figures nobody saw). The reason, the person's name (from the token's `name` claim, may be empty) and the figures are recorded with the price and announced as `price.set`.
  - **A price for a piece that holds nothing** is saved and the answer says `NO_COST_KNOWN` ("no cost known"): there is nothing to compare with. It is re-judged on every later read.
  - **Dating.** `effectiveFrom` is optional: default now. It may be **earlier, up to 72 hours back** (a paper tag changed this morning and keyed tonight; each row also records when it was keyed), **never in the future** and **never before the price it follows** (400 `effective-date-in-the-future`, `effective-date-too-old`, `effective-date-before-latest-price`). Saving the price it already has, in the same currency, is 400 `nothing-changed` (the same figure in another currency is a change: a legacy dollar piece is moved to Kwacha by sending `currency: "ZMW"`, even at the same number).
  - **Failures to word for a person:** 503 `cost unavailable` with `Retry-After` (stock could not be asked, nothing saved: "try again in a moment"), the same 503 also answers, since Phase 7, when promotions could not be asked (nothing saved), 502 (a fault between the services: "tell whoever looks after the system"), 409 `concurrent-update` (the default box changed while the cost was being read: retry).
- **Where every price stands** — `GET /api/v1/admin/pricing/below-cost?status=BELOW|NO_COST_KNOWN|CURRENCY_MISMATCH|OK|ALL&page&size` (default BELOW, biggest shortfall first). It is computed from the stock held **now** at every read, so a dearer lot received, a cost corrected, a dear lot sold out of or a changed default box all appear the next time anyone looks (this is how "re-runs" is met: nothing is stored that could go stale). `counts` gives every status whatever the filter, for a badge. Nothing tells anyone when a price falls below cost until Phase 11 reads this list (the plan's hand-off); show it prominently.
- **Suggested price** — only a suggestion, never applied: `landedCost × (1 + p/100)`, rounded **up** to the ngwee, where landed cost is the same floor the warning uses. `p` comes from `targetProfitPercent` on the read or, if the owner has set `oriah.catalog.pricing.target-profit-percent`, the configured value. **The month's overhead share is not built** (it needs Phase 10's expenses); show the suggestion without it.
- **Default packaging** — `PUT /api/v1/admin/products/{id}/default-packaging` with `{packagingVariantId}` (an active variant of a packaging entry; `null` clears). 400 if it is not a usable box, 409 if the product is itself packaging. The product's admin reads carry `defaultPackagingVariantId`. Changing it changes the floor (the box's dearest held cost is added). **A box that products go out in cannot be deleted:** `DELETE /api/v1/admin/products/{id}` of a packaging entry is **409 `packaging-in-use`** with a `products` list (`id`, `title`) of the ones that hold it; the screen shows them and asks the person to choose another box for each (or none) first. A product that has itself been deleted no longer holds its box.
- **Boxes set aside** — INVENTORY_ADMIN, under the inventory admin prefix. `PUT /api/v1/admin/inventory/box-commitments/{productId}` with `{quantity}` (a whole number ≥ 1); the box is the product's default box. Again for the same product it **replaces** the record. The answer carries the record and the box's counts (`onHand`, `committed`, `reserved`, `free`). Refused with 409 `insufficient-free-packaging` and **`available`** (the most that can be set aside for this product) when there are not enough free; 409 `no-default-box`, `product-state-not-received` (inventory has not heard of the product yet: any save of it in the catalogue sends it; retry), `not-a-sellable-product`. `DELETE .../{productId}` lets them go (204, 404 if none). `GET .../box-commitments?productId=&boxVariantId=` lists the records and `GET .../{productId}/history` says what was done (ALLOCATE, REPLACE, RELEASE, CONSUME, WRITE_OFF_CUT) with who and when. **Automatic release:** unpublishing, deleting or changing the default box lets the boxes go (within a moment, by Kafka). **Amended in Phase 7:** each record in the list also carries `held` (the set-aside boxes that live orders hold right now; the `PUT` answer does not), `quantity` is the whole promise, and a `PUT` below `held` is 409 `held-by-reservations`; see Phase 7, Stock screen.
- **Packaging counts on the stock screen** — `GET /api/v1/admin/inventory` rows now carry `committed` and `free` (`onHand == free + committed + reserved`); `available` is the same figure as `free`.
- **Write-off screen** — the reply of a box write-off carries `committed`, `free` and **`cutCommitments`** `[{productId, boxVariantId, cut}]`: name those products ("these pieces just lost their set-aside boxes"). Free boxes go first; set-aside boxes are cut only for what free cannot absorb, newest first. A take-back returns boxes to free and never re-sets them aside.
- **Publish is its own step** after pricing (`POST /api/v1/admin/products/{id}/publish`, unchanged), and there is an **Unpublish** action: `POST /api/v1/admin/products/{id}/unpublish` (ACTIVE back to DRAFT; 409 if it is not published). Publishing does not re-check the cost (nothing can be sold without stock): the pricing list is where a below-cost price is seen.

**Storefront**

- None. The shop shows a published piece at its price in force, and landed cost never reaches a shopper.

**What it breaks in oriah-web today**

- `repriceVariant` (`PATCH /api/v1/admin/products/{id}/variants/{variantId}`) is **gone** and a variant can **no longer be created with a price** (a price above 0.00 is 400 naming the field). The product dialog's single Price box must move to the pricing screen. `AdminProductsClient.test.tsx` and `adminProductFlow.test.ts` change with it.
- `admin-happy-path.spec.ts` types the price into the create dialog and expects the piece on `/products` immediately. In the real order the price comes after receiving, via the pricing endpoint with both roles.
- The generated OpenAPI types change (removed `repriceVariant` and `VariantUpdateRequest`; new `Pricing (admin)` and `Box commitments (admin)` tags).

### Phase 7 — Sell

> **Status: the API is built (2026-11-14). The screens are not.** Everything below is the API **as built**, taken from the code, from the OpenAPI captured from the live stack (`oriah-api/.codex-tmp/current/openapi/<service>.json`), from the Phase 7 commits and from the live smoke test (`smoke-test.ps1`, steps 2b to 6i, 10, 20, 20b and 20e, which passed on the full container stack on 2026-11-14 and are worked examples of every request here). It replaces the plan-time guesses this section held before. Money is Kwacha (ZMW) to the ngwee. Three small checkout changes were made after that OpenAPI capture and are marked "(after the capture)" below: the pass-through of `live-order-has-another-address`, a new `order-no-longer-held` answer, and a 400 for an `Idempotency-Key` longer than 128 characters.

**How a sale runs now, in order** (the screens must follow this, not the old "pay by card at checkout"):

1. The shopper's bag is priced (**preview**). Once they choose how it reaches them, preview also gives a total and a fingerprint of that quote (`quoteDigest`).
2. **Confirm** places the order and **holds** the pieces, and a box for each piece, for the shopper: 10 minutes by default. Checkout touches no money. A 200 means "placed and held", never "paid".
3. The shopper pays outside the system, by mobile money or bank transfer, then tells Oriah how (**payment claim**: method and reference). That stretches the hold to at most a day from when it was first taken. The order is now `PAYMENT_SUBMITTED`.
4. Staff look in the provider's or bank's records, then **confirm the money** (or **reject** a claim that is false).
5. The rest is automatic and takes seconds: order asks inventory to **sell** the held pieces (boxes included), dated to the day the money arrived, then the order becomes `PAID` and is given a receipt number (`OR-` and six digits). If the money cannot settle the sale (wrong amount, order cancelled, piece already sold, order already paid) it is **held for the customer**, owed back, and listed as held money. Nothing is ever refused just because the amount was wrong.

**Who may do what.** A capability is a permission the code checks; a person holds capabilities through a job role. `SALES_AGENT`: OWNER, MANAGER, SALES. `ORDER_ADMIN`, `SHIPPING_ADMIN`, `CATALOG_ADMIN`: OWNER, MANAGER. `COST_VIEWER`: OWNER, MANAGER, BOOKKEEPER. `PAYMENT_ADMIN`, `BACKDATE_SALE`: OWNER only. A shopper holds `USER`. Hide a screen unless the person holds its capability (`oriah-web/src/lib/auth/capabilities.ts`); a missing one is 403 at the gateway.

**Errors, in general.** Every refusal is `application/problem+json`, and its `type` is `https://oriah.dev/problems/<name>`: branch on the `<name>` (as `src/lib/api/checkoutErrors.ts` does with `problemType()`). **A 400 comes in two shapes.** A request that fails validation (a missing or malformed field) has `type` `validation` and lists `fieldErrors` (`field`, `message`), one per field at fault. A request that breaks a business rule (cash claimed online, an unusable reference, an address that is not the shopper's, and most of payment's, shipping's and promotion's rule-based 400s) has `type` `bad-request` and a plain `detail` and **no `fieldErrors`**: the screen must show `detail` (or its own words) when `fieldErrors` is absent. Some 400s have a name of their own (`unsupported-currency`). Names below are exact.

**Old open questions this build settled** (each was open in the plan-time text of this section; how it came out is here, and the screens must follow it):

- *Does self-collect need a published price per town?* No. Self-collect is always offered at K0.00, needs no town and cannot be switched off.
- *Can admin add a named courier?* Yes, a `COURIER` or a `BUS_PARCEL` service, through `POST /api/v1/admin/shipping/options`. Seeded: `OWN_DELIVERY` ("Oriah delivery"), `YANGO`, `PLATINUM`, `EMS`. Own delivery and Yango are not added by admin: they are seeded.
- *Which capability swaps a box after payment?* `ORDER_ADMIN` (OWNER and MANAGER, not SALES).
- *Which queue may a SALES person read?* `GET /api/v1/admin/orders/awaiting-payment`, `SALES_AGENT`. (`GET /api/v1/admin/orders` stays `ORDER_ADMIN`.)
- *Can the confirmation form record money that does not settle the sale?* It never refuses on amount: payment records any amount, and order decides. A wrong amount is held for the customer and the order stays as it was (see Confirm money).
- *Which path lists money held for customers, and who sees it?* `GET /api/v1/admin/payments/held-money`, `PAYMENT_ADMIN` (OWNER only). Confirm, claims, rejections, the pending list and voids are `SALES_AGENT`.
- *Does saving a promotion that goes below cost need a typed reason?* No. A promotion is never refused and asks for no reason; it is warned about and listed (see Promotions).
- *Where is the box chosen?* At **placement**, not at confirmation: the hold takes the piece and the product's default box together. A box that has run out makes placement fail with `insufficient-stock` naming the box. Changing the box is possible only after payment (see Box swap).
- *May a shopper submit a reference on an EXPIRED order?* No: 409 `order-not-awaiting-payment`. Money that arrives later for an expired order is confirmed by staff (late confirmation, below).
- *May a shopper cancel their own unpaid order?* The backend allows it while the order is `CREATED` (waiting, no reference given yet). Whether to offer the button is still a screen decision.
- *Are the three times configurable?* Yes: the hold `oriah.sales.hold` (PT10M), the longest hold after a claim `oriah.sales.payment-submitted-hold` (PT24H), the back-dating window `oriah.payment.backdate-window` (PT72H).

**Admin screens**

- **Delivery screen** (`SHIPPING_ADMIN`, all under `/api/v1/admin/shipping/`). Every change to something that already exists sends the `version` it read; **409 `stale-version`** means someone else changed it first (reload, carries the current version). A database outage is 503 `shipping-unavailable`.
  - **Provinces and towns.** `GET /provinces` gives the ten provinces (`id`, `code`, `name`, `towns` count). `GET /towns?provinceId=&active=` gives `id`, `provinceId`, `provinceName`, `name`, `slug`, `active`, `version`. About forty main towns are seeded, **with no prices**. Add one: `POST /towns {provinceId, name}` (up to 80 characters), 201; 404 `province-not-found`; 409 `town-exists`. Switch one: `PATCH /towns/{townId} {active, version}`. A town is never deleted, because orders point at it.
  - **Options.** `GET /options` gives `code`, `name`, `kind` (`OWN_DELIVERY`, `YANGO`, `COURIER`, `BUS_PARCEL`), `active`, `position`, `version`. Add: `POST /options {name, kind}` where `kind` is `COURIER` or `BUS_PARCEL`, 201 (the `code` is made from the name); 409 `option-exists` carries the `code`. Switch: `PATCH /options/{code} {active, version}`, 404 `option-not-found`.
  - **Prices, dated and never seeded.** A price is a draft until published, then history. `POST /prices {townId, optionCode, amount, allowsOriahCollects (default true), allowsRecipientPays (default false), etaDaysMin, etaDaysMax}` makes a **draft** (201; 404 `town-not-found` or `option-not-found`; 409 `draft-exists` names the draft: one draft per town and option). `PUT /prices/{priceId} {amount, allowsOriahCollects, allowsRecipientPays, etaDaysMin, etaDaysMax, version}` edits a draft. `DELETE /prices/{priceId}?version=` discards a draft (204). `POST /prices/{priceId}/publish {version}` makes it the live price of that town and option; the one it replaces becomes `SUPERSEDED` history and is kept. A price id that does not exist is 404 `price-not-found` for an edit, a discard or a publish. 409 `price-published` for any edit, discard or publish of a price that is no longer a draft. `GET /prices?townId=&optionCode=&status=` (`DRAFT`, `PUBLISHED`, `SUPERSEDED`) gives `id`, `townId`, `townName`, `optionCode`, `amount`, `currency`, the two payer flags, the two day counts, `status`, `version`, `createdAt`, `createdBy`, `publishedAt`, `publishedBy`, `supersededAt`. 400s: `amount` is whole ngwee and not negative; at least one payer must be allowed; give both ends of the delivery time or neither. **A shopper sees nothing until a price is published.**
  - **Which payer.** `allowsOriahCollects` means Oriah collects the charge with the order. `allowsRecipientPays` means the recipient may pay the courier on arrival, and then the order carries K0.00 for delivery. A price may allow both, and then the shopper chooses.
  - **A town not yet offered** is handled here: get the courier's figure, add the price as a draft, publish it. There is no "awaiting quote" state and no province-wide fallback price. A town is listed to shoppers only when it is switched on and has an option that is switched on with a published price.
  - **Free-delivery threshold.** `GET /settings` gives `freeDeliveryThreshold` (null while off, the default), `currency`, `version`, `updatedAt`, `updatedBy`. `PUT /settings {freeDeliveryThreshold, version, reason}` sets it (above K0.00, whole ngwee) or switches it off with null; `reason` is up to 200 characters. `GET /settings/changes` lists every change (`thresholdBefore`, `thresholdAfter`, `changedAt`, `changedBy`, `reason`), newest first. It is judged on the **goods after discount**: when the goods reach it (equal counts), delivery that Oriah collects is K0.00.
- **Confirm money** (`SALES_AGENT`, `/api/v1/admin/payments/confirmations`).

  - **409, nothing ordered:** `cart-empty`; `pricing-changed` (the bag, a price, a promotion, or the delivery or its price moved since preview; carries `changedLines`; preview again, show the new quote, confirm with its digest); `bag-not-purchasable`; `mixed-currency`; **`insufficient-stock`** (a piece or its box is gone: carries `shortages`, each `{variantId, kind: "GOODS" or "BOX", requested, available}`, naming every short line; all or nothing, nothing held; say "no longer available"); **`hold-limit-reached`** (a shopper may hold 3 live orders and 20 pieces at once; carries `heldOrders`, `heldPieces` and `maxLiveOrders` or `maxHeldPieces`); `idempotency-key-reused`; `live-order-has-another-address` (carries `orderId`; after the capture); `no-default-box`, `not-a-sellable-product`, `product-state-not-received` (a piece staff have not finished setting up: say it cannot be ordered right now); and shipping's `town-not-offered`, `payer-not-offered`, `town-not-found`. **`order-no-longer-held`** (after the capture; carries `orderId`, `orderStatus`): a repeated key found its order already `EXPIRED` or `CANCELLED`, so nothing is held: confirm again with a **new** key.
  - **400:** two shapes. *Field errors* (`type` `validation`, with `fieldErrors`): a missing or malformed `quoteDigest`, a missing address or town, a town or payer sent with `SELF_COLLECT`. *A plain `bad-request` with a `detail` and no `fieldErrors`*: an address that is not the shopper's ("That shipping address is not one of yours.") and an `Idempotency-Key` over 128 characters (after the capture). Show `detail`, or your own words, when `fieldErrors` is absent. **500:** a fault of ours; do not retry blindly, send the shopper to their orders if it persists. **402, 422 and 502 can no longer happen.**
  - **503, with `Retry-After: 5`: a dependency is unavailable, and the order may or may not have been placed** (a reply can be lost). Offer "Try again" on a 503 and nothing else, **with the SAME `Idempotency-Key`**: order then hands back the order it already made, never a second. Generate one key per submission and reuse it for every retry of that one submission; mint a new one only for a new submission (a changed bag, or a new preview after `pricing-changed`).
  - **After a lost reply, the bag may already be empty.** The bag is cleared the moment the order is placed, so a retry then answers **409 `cart-empty`**. On `cart-empty` after any confirm whose reply was lost (a 503, a timeout, a dropped connection, a 500), **do not say only "your bag is empty": send the shopper to My orders**, where the order is waiting with its hold time. Likewise a retry with the same key that answers 409 `idempotency-key-reused` means an order already exists for that key with a different quote or address: send them to their orders.
  - **Safe to repeat.** The same key answers the same order (200). A new key for the same bag finds the live order by the quote's digest and answers it (200) instead of placing a second. The same bag for **another address** is 409 `live-order-has-another-address`.
  - **The 30 s proxy limit** (Phase 1's must-do) still stands: set the storefront proxy timeout explicitly above checkout's worst confirm. Checkout now waits up to 20 s for order (it was 15 s), because order's placement makes five calls (15.5 s of budget).
- **Payment step: the 4242 card form goes.** The shopper pays Oriah directly, by mobile money or bank transfer, to the details the owner supplies (no backend setting holds them), then reports it: `POST /api/v1/orders/{id}/payment-claim` (`USER`, the shopper's own order) `{method, reference}`. `method`: `MTN`, `AIRTEL`, `ZAMTEL` or `BANK_TRANSFER` (any letter case; **cash is paid in person and is 400**). `reference`: any spelling, spaces and letter case do not matter, 3 to 64 letters, digits and `. _ - /`; the same claim again is 200 and changes nothing. 200 returns the order, now `PAYMENT_SUBMITTED`; the hold is stretched to at most a day from when it was first taken (`holdExpiresAt` can arrive a moment later, so re-read the order). It is **not money**: staff confirm it, or say they cannot find it. Refusals: 400 (cash, a method that is not one of the four, or a reference that is not usable: `type` `bad-request` and a `detail` only, with no `fieldErrors`, so show the `detail` or your own words; a blank method or reference, a method over 32 characters or a reference over 100 is a field error); 404 (not the shopper's order, or no such order: the same answer); 409 `payment-already-submitted` (a different reference after the first: the shopper cannot correct a typo, see the owner list), `order-not-awaiting-payment` (the order is `PAID`, `EXPIRED`, `CANCELLED` and so on), `order-not-held`, `hold-expired` (the pieces are no longer held: place the order again), `payment-being-applied`.

### Phase 8 — Deliver

**Built (backend, 2026-11-15); the frontend is not changed.** After staff confirm the money an order is PAID. A packer or driver (job role `DISPATCH`, capability
`FULFILMENT_AGENT`; the owner and the manager hold it too) packs it, sends it by the option the shopper chose and records the courier fare when Oriah pays one,
then marks it delivered; a pickup is packed and handed over. **The packer reads no money** (Q29).

**Admin screens (FULFILMENT_AGENT)**

- **Work list** `GET /api/v1/admin/orders/dispatch/queue?stage=` with `stage` `TO_PACK` (the default), `PACKED` or `ON_THE_WAY` (anything else is 400): paid orders, oldest
  payment first, at most 100. Reply `{stage, count, orders: [{orderId, receiptNumber, status, stage, optionName, payer, townName, recipientName, pieces, paidAt, packedAt,
  dispatchedAt, packable}]}`; absent fields are left out. `packable: false` marks an order placed before Phase 8 that has no recipient or address kept (an order
  administrator supplies them, below). A pickup has no `optionName`, `payer`, `townName` or `recipientName`.
- **Packing slip** `GET /api/v1/admin/orders/{id}/dispatch`: `orderId, receiptNumber, status, stage, paidAt, selfCollect, fareDue, boxSwapInProgress,
  delivery{optionCode, optionName, payer, townName, recipientName, recipientPhone, address{line1, line2, city, state, postalCode, country}}` (absent for a pickup, and
  after DELIVERED except to an order administrator), `lines[{lineId, title, quantity, box{variantId, name}}]` (by title; `name` is catalog's, e.g. "Velvet box / Large"),
  `boxNamesAvailable` and `boxNamesProblem` (`unavailable` or `forbidden`: show the box id and say names could not be read; the slip is still 200), `packedAt`,
  `dispatchedAt`, `reference`, `farePaid` (only for someone who may see cost, COST_VIEWER), `deliveredAt`. **No total, price, discount, waiver, login or actor is ever on
  it.** 409 `order-not-paid` for an unpaid or cancelled order. Show `boxSwapInProgress` loudly: a box swap is still with inventory, packing and shipping are refused.
- **Steps**, each `POST /api/v1/admin/orders/{id}/dispatch/pack | ship | deliver` with a JSON body (`{}` is enough), each answering `{orderId, status, stage, packedAt,
  dispatchedAt, deliveredAt, reference, farePaid?, replay}`:
  - `pack` (PAID to FULFILLED); `ship` (FULFILLED to SHIPPED) with `reference` (optional: waybill, booking or bus receipt, letters, digits, space and `. / # -`, 1 to 40) and

### Phase 9 — Phone orders

**Built (backend, 2026-11-15); the frontend is not changed.** Staff (`SALES_AGENT`: job role `SALES`, and the owner and manager) record a sale taken by phone, WhatsApp or on paper for a caller
with no account. All paths are `/api/v1/admin/orders/recorded...`; a **salesperson reads no landed cost or margin (Q29)**: never call `/admin/costs/**`, `/admin/pricing/**` or
`/admin/orders/{id}` (ORDER_ADMIN) from these screens, and do not rely on hiding: the API refuses.

**The "record a sale" screen**

- **Choose the kind first:** *Taking an order now* (`LIVE_PHONE`) or *Typing in a sale from paper* (`LATE_PAPER`). For paper: the date it happened (`occurredAt`, any age; a date more than 72 hours
  ago is 403 unless the person holds `BACKDATE_SALE`, so show it as "ask the owner"), **a reason (5 to 200 characters, always)** and the slip number if the paper has one.
- **Caller:** name (always), phone (required for a delivery, optional for a counter pickup; typed any Zambian way: `097 123 4567`, `+260 97 ...`). **Lines:** a piece and a quantity each, and
  the box: the product's default unless the person picks another from `GET /recorded/boxes` (`[{variantId, title, variantTitle, sku}]`, no price). **Delivery:** a pickup; or a delivery,
  where the person picks an option and a town from `GET /recorded/delivery-places` (`{provinces[{id, name, towns[{id, name}]}], options[{code, name, kind}]}`, no prices), says who pays the courier
  (`ORIAH_COLLECTS` or `RECIPIENT_PAYS`) and, for Oriah's charge, types the amount **agreed by phone** (`delivery.mode: "AGREED"`, `agreedAmount`); the shop's own published price is `mode: "PUBLISHED"`
  (a live sale only). Own delivery can never be recipient-paid (the screen should not offer it). The recipient defaults to the caller; **the address line is required for a delivery**.
- **There is no price, discount or total box (Q12).** Call `POST /recorded/preview` with the same body (the caller may be left out) as the person fills it in: it answers `{kind, occurredAt,
  currency, lines[{title, quantity, unitPrice, discountPerPiece, lineTotal}], subtotal, discountAmount, delivery, total}`. Show the total, let the person read it to the caller, and send it as
  `expectedTotal` when recording: **a different total is 409 `total-differs`** (it names the real total: re-read it to the caller). Promotions apply by themselves, priced as of the sale's own day.
- **Record** with `POST /recorded` and a required `Idempotency-Key` (a UUID made when the form opens, **kept if the request is repeated**: a repeat is 200 with the same order). 201 answers the
  order (`status CREATED`, `holdExpiresAt` ten minutes on): tell the person **to confirm the money now** (the existing payment confirmation screen, `POST /api/v1/admin/payments/confirmations`: cash, MTN,
  Airtel, Zamtel or bank, with the day the money arrived). Money confirmed after the hold lapsed still pays the order if its pieces are free; if not, it is held for the caller.
- **Errors, all with a plain `detail`:** 400 `invalid-contact` (a name or phone that cannot be read), `invalid-delivery`, `delivery-reason-required` (an agreed amount different from the shop's own quote needs
  `agreedReason`, 5 to 200 characters, higher or lower), `invalid-occurred-at`, `backdate-reason-required`; 403 a paper sale older than 72 hours without `BACKDATE_SALE`; 409 `total-differs`,
  `zero-total-not-supported` (a sale that comes to K0.00 cannot be recorded: a gift goes through the stock give-away screen), `no-price-at-date` (the piece had no price on that date: it cannot be recorded
  at that date, **say so and name the piece; a sale is never priced at today's price**), `late-sale-delivery-must-be-agreed`, `delivery-place-not-offered` (the town or option is not on the list: **the owner
  adds it**), `town-not-offered`, `insufficient-stock` (names each short piece or box: pick another box), `idempotency-key-reused`; 503 catalog, shipping or inventory did not answer (nothing was saved: try again).

**After recording**

- **Find an order:** `GET /recorded?q=&status=&page=&size=` (`q`: the caller's phone in any spelling, a receipt number `OR-nnnnnn`, a slip number, or the first 3+ letters of a name; at most 50 a page,
  newest first; a row is `{id, status, kind, occurredAt, placedAt, callerName, callerPhone (masked), total, currency, receiptNumber}`).
- **One order:** `GET /recorded/{id}`: caller, recipient and address **while the order is alive** (a hold that lapsed still needs its caller rung: show the phone), lines, discount, delivery and its
  source (`PUBLISHED` or `AGREED`), total, `receiptNumber`/`paidAt` once paid, and `dispatch{packedAt, dispatchedAt, deliveredAt}`; after DELIVERED the phone is masked and the recipient and address are
  gone. **Show the channel and the caller's name in the admin order list** (`GET /api/v1/admin/orders` and `SalesQueues` gain `channel` for ORDER_ADMIN; the recorded list is the salesperson's own).
- **The receipt for the caller:** `GET /recorded/{id}/receipt` (409 `receipt-not-ready` until paid): `{receiptNumber, paidAt, callerName, currency, lines[...], subtotal, discountAmount, delivery{optionName,
  townName, payer, amount, note}, total, notice}`. It is OUR receipt, **never a tax invoice, no VAT line** (show the `notice`), has the caller's name only (no phone or street: it may be forwarded) and, for a
  courier the recipient pays, says "you pay the courier directly: K0.00 on this receipt". Telling the caller it is ready is **manual until Phase 11**: staff ring them from the order's phone.
- **Cancel** while it waits for money: `POST /recorded/{id}/cancel` (a paid order is 409: a paid sale is undone by a return, Phase 12). A lapsed (EXPIRED) order is NOT cancelled by sales: it may still be paid.
- **A paper sale's money must carry the day of the sale.** If staff confirm it on another day, payment HOLDS it (`WRONG_DATE`: it appears in held money and in the settlements list) and the order is not paid:
  **void that confirmation and key the money again with `arrivedAt` = the day of the sale** (the person confirming a sale older than 72 hours needs `BACKDATE_SALE`).
- The packer's work list and slip (Phase 8) work for a phone order as for any: a pickup's slip carries the **caller's name** for the person to hand it to, never the phone.

**What it breaks in oriah-web today**

- **A `PHONE` order has no `keycloakId`:** `OrderSchema` must tolerate it (it already tolerates a missing one) and the admin order screens must show `channel`. A shopper never sees a phone order.
- **Checkout must keep never sending a delivery amount:** a confirm body carrying `deliveryAmount`, `shippingAmount` or `total` is now **400** (it was ignored). Declare no such field.
- No Playwright spec reaches the recorded-order screens.

**Needs from the owner** (none blocks the build; the plan lists them with the reasons)

1. Must a caller give a name and phone? (built: a name always; a phone for a delivery, optional for a pickup.) 2. May staff sell a piece that is priced but **not shown on the website** (built: yes, the staff
price read ignores publication)? 3. How long may a late payment still be accepted, and when may a caller's details be erased (built: no limit on payment and no erasure: one decision, not two)?

11. Who rings the caller when the parcel is ready, until messages exist? 12. Who adds a town or a bus-company option that is not on the list?

### Phase 12 — Returns, refunds and exchanges
