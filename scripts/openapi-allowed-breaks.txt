# ---------------------------------------------------------------------------
# Pricing phase: cart stops accepting a price, and caps a quantity.
# ---------------------------------------------------------------------------
#
# AddItemRequest loses unitPrice and title.
#
# The client may no longer name a price. POST /api/v1/carts/me/items with
# "unitPrice": 0.01 bought a K4,500 ring for one cent -- demonstrated live
# against the running stack, not inferred. cart-service now resolves the price
# from catalog's POST /api/v1/variants/pricing before any mutation. Keeping the
# property for compatibility would leave the hole reachable, which is the whole
# reason it goes; there is no additive version of this change.
#
# title goes with it because the line label is now catalog's composed
# variantTitle rather than a client string stored verbatim. Side benefit: the
# old field carried @NotBlank with no @Size against a VARCHAR(255) column, so a
# 256-character title was a DataIntegrityViolationException rendered as a 500.
#
# Two findings, not one: openapi_diff.py iterates properties individually.
#
# What a stale client actually experiences: cart sets no spring.jackson block,
# so FAIL_ON_UNKNOWN_PROPERTIES=false applies and a request still sending
# unitPrice is accepted with the field IGNORED and the catalog price used. So
# the break is in the published schema rather than in behaviour -- a storefront
# mid-deploy keeps working and quietly starts getting correct prices. oriah-web
# sends this body, it does not parse it, so no Zod schema throws (the gate's
# generic note about Zod applies to response types).
#
# The quantity caps are a NARROWING, and the gate is right to call it breaking.
#
# Adding maximum: 99 to AddItemRequest.quantity and UpdateItemRequest.quantity
# means a request the server used to accept is now a 400. That is deliberate
# and it replaces something worse: CartItem.bump was `this.quantity += by` on an
# Integer with no maximum anywhere, so a large quantity wrapped negative and the
# row was rejected by V1's CHECK (quantity > 0) -- a 500. Every real client is
# strictly better off: 99 is far past any plausible purchase of a piece of
# jewellery, and what used to be a 500 is now a 400 with fieldErrors naming the
# field.
#
# The map for this phase predicted three findings in total and missed both of
# these; they were found by running the gate rather than by reading the plan.
#
# Reviewed and accepted 2026-10-13.

cart|schema property removed|AddItemRequest.unitPrice
cart|schema property removed|AddItemRequest.title

# ---------------------------------------------------------------------------
# Pricing phase: confirm must prove which prices the shopper agreed to.
# ---------------------------------------------------------------------------
#
# ConfirmRequest gains a REQUIRED pricingVersion.
#
# Preview quotes a bag and the shopper reads a total; between that and Place
# order an admin can reprice a variant or withdraw it. The version is a digest
# of the prices preview used, echoed back on confirm, so the server can tell
# whether the shopper is agreeing to the numbers it actually showed them --
# and refuse rather than silently charge different ones.
#
# REQUIRED is the whole guarantee, and that is why this break is taken. A
# nullable version would let any client opt out of the staleness check by
# omitting the field, which is the one thing the check exists to prevent.
#
# The schema NAME stays ConfirmRequest. Renaming it to ConfirmRequestV2 would
# produce three more findings (schema removed, requestBody schema changed, plus
# this one) and nothing would be gained: the operationId, the path and every
# other property are unchanged.
#
# The token is only ever COMPARED against a value recomputed server-side from
# catalog, never used as an input to a price, so a forged value buys nothing --
# the worst a client can do with a wrong one is refuse its own checkout.
#
# Client impact, checked rather than assumed: oriah-web's PreviewResponseSchema
# had to declare pricingVersion before the storefront could echo it, because
# Zod strips undeclared keys silently. Without that one line the token arrives,
# is discarded, confirm sends nothing and EVERY checkout 409s -- so this break
# is paired with a storefront change in the same phase rather than left for a
# client to discover.
#
# Reviewed and accepted 2026-10-13.

# Retired 2026-11-08: pricingVersion was replaced by quoteDigest (Phase 0,
# item 4.4, below), so this waiver no longer matches anything and is kept only
# as history.
# checkout|property became required|ConfirmRequest.pricingVersion

# ---------------------------------------------------------------------------
# Phase 7, step 27: payment's create-intent input surface was unbounded.
# ---------------------------------------------------------------------------
#
# Three deliberate TIGHTENINGS of what the server accepts. Verified live
# against the running stack before and after:
#
#   currency omitted   -> was 201 with currency silently "USD"; now 400
#   currency "zmw"     -> was 201 stored as-is;                  now 400
#   amount 1e11        -> was 500 from the NUMERIC(12,2) column; now 400
#
# Why each is not merely cosmetic:
#
# * The USD default was a hardcoded currency on a platform priced in Kwacha,
#   and it was written in TWO places that had to agree -- PaymentService
#   .createIntent and the PaymentIntent constructor. Requiring the field
#   removes the decision rather than centralising it: nothing has to guess
#   which currency money is in.
#
# * Case matters twice. order-service's PaymentIntentVerifier compares the
#   intent's currency to the order's with equals(), so a lower-case intent
#   could never settle an upper-case order; and AdminPaymentSummary groups
#   captured totals BY currency, so "zmw" and "ZMW" split one figure into two
#   rows that each read as the whole.
#
# * The amount ceiling is the column's real capacity, not a round number.
#   Exceeding NUMERIC(12,2) reached Postgres, violated CHECK (amount > 0)'s
#   sibling precision limit, and surfaced through the shared advice as
#   "500 An unexpected error occurred" -- which tells the caller nothing it
#   can act on and records an ordinary bad request as the server fault an
#   operator pages on. A column is a backstop; if it fires again, a 500 is
#   then the honest answer.
#
# Taken because there is exactly ONE runtime caller of POST /intents and it
# already complies. checkout-service builds its own
# PaymentClient.CreateIntentRequest record and always passes
# priced.currency(), which reprice() guarantees non-null and upper-case:
# CatalogPricingClient.Entry.isPriced() requires a non-blank currency, and
# confirm throws CartEmptyException before reprice() runs, so there is no path
# that reaches payment without one. Checked, not assumed.
#
# oriah-web was checked too: src/lib/api/generated/payment.ts carries a
# createIntent type because codegen emits the whole spec, but NOTHING outside
# that generated file references createIntent or the /payments/intents path.
# The storefront confirms intents through checkout; it never creates one. So
# the generated type will change on the next `npm run codegen` and no call
# site changes with it.
#
# Not waived, and worth recording as the gate earning its keep: the first
# version of this change replaced @Size(min=3,max=3) with @NotBlank, which
# dropped maxLength:3 from the published schema and left a LOOSER contract
# beside a stricter server. The gate caught it and @Size was restored, which
# is why the currency entry below shows only a pattern being added.
#
# Reviewed and accepted 2026-10-13.
payment|property became required|CreateIntentRequest.currency
payment|schema property type changed|CreateIntentRequest.amount: {"minimum": 0.01, "type": "number"} -> {"maximum": 9999999999.99, "minimum": 0.01, "type": "number"}
payment|schema property type changed|CreateIntentRequest.currency: {"maxLength": 3, "minLength": 3, "type": "string"} -> {"maxLength": 3, "minLength": 3, "pattern": "^[A-Z]{3}$", "type": "string"}

# ---------------------------------------------------------------------------
# Phase 7, step 27: order's place-order input was unbounded too.
# ---------------------------------------------------------------------------
#
# Six deliberate TIGHTENINGS, same reasoning as payment's above. The database
# was the only line of defence and it answers in 500s. Verified live before and
# after:
#
#   quantity -5 / 0        was 500 from CHECK (quantity > 0)   -> now 400
#   quantity 2000000000    was 500, NUMERIC(12,2) overflow      -> now 400
#   title 5000 chars       was 500 from title VARCHAR(255)      -> now 400
#   unitPrice -100.00      was 500 from CHECK (unit_price >= 0) -> now 400
#   currency omitted       was 201 with currency "USD"          -> now 400
#   currency "zmw"         was 201 stored as-is                 -> now 400
#
# The caps mirror cart's: MAX_LINES 100 and MAX_QUANTITY_PER_LINE 99. The
# shared reason is catalog's pricing endpoint enforcing @Size(max = 100) on a
# batch, which is why cart caps a bag at 100 -- and an order is the record of a
# bag, so an order that could not have been a bag should not be constructible.
# Once order prices from catalog itself, that batch limit applies to it
# directly.
#
# The quantity ceiling is not cosmetic. quantity is the one multiplier the
# client still controls, and it is about to be the only one: an unbounded
# integer against an AUTHORITATIVE unit price overflows orders.subtotal
# NUMERIC(12,2) into a 500. All three candidate designs for making order the
# pricing authority proposed @Positive and no @Max, and all three judges
# flagged it independently.
#
# currency: Order's constructor read
#   this.currency = currency == null || currency.isBlank() ? "USD" : currency;
# on a platform priced in Kwacha. It was the LAST hardcoded currency in live
# code -- cart and catalog hold DEFAULT_CURRENCY = "ZMW", shipping's is
# configuration, payment's identical default went in the same pass. The
# constructor now refuses rather than defaulting to ZMW, because an order is
# the record of a sale: a default, even the right one, produces an order whose
# currency nobody chose.
#
# Taken because no client breaks:
#
# * oriah-web never POSTs /orders. It carries a generated PlaceOrderRequest
#   type (codegen emits the whole spec) but nothing outside
#   src/lib/api/generated/ references it -- the storefront places orders
#   through checkout's confirm. Checked, not assumed: the only `placeOrder`
#   matches in src/ are the `canPlaceOrder` prop in CheckoutClient.
# * checkout builds its own OrderClient.PlaceOrderRequest record and always
#   sends priced.currency() -- non-blank and upper-case, guaranteed by
#   Entry.isPriced() -- with quantities from the bag, which cart caps at 99
#   per line and 100 lines.
# * smoke-test.ps1's New-ProbeOrder (:925-934) posts currency "USD",
#   title "Authz probe", quantity 1 and unitPrice 4500.00, all inside the new
#   bounds. The live exploit harness keeps working unchanged.
#
# Not waived, and the gate's second catch this phase: the first version used
# @NotEmpty @Size(max = 100) on items and @NotBlank @Size(max = 255) on title.
# springdoc derives minItems/minLength from @Size and NOT from
# @NotEmpty/@NotBlank, so the published schema lost minItems: 1 and gained
# minLength: 0 -- telling every generated client an empty order and a blank
# title were acceptable while the server still refused them. Explicit mins
# were added. A looser published contract beside a stricter server is worse
# than no contract, because a client trusts it.
#
# Reviewed and accepted 2026-10-13.
order|property became required|PlaceOrderRequest.currency
order|schema property type changed|LineItem.quantity: {"format": "int32", "type": "integer"} -> {"format": "int32", "maximum": 99, "minimum": 1, "type": "integer"}
order|schema property type changed|LineItem.title: {"type": "string"} -> {"maxLength": 255, "minLength": 1, "type": "string"}
order|schema property type changed|LineItem.unitPrice: {"type": "number"} -> {"minimum": 0.0, "type": "number"}
order|schema property type changed|PlaceOrderRequest.currency: {"maxLength": 3, "minLength": 3, "type": "string"} -> {"maxLength": 3, "minLength": 3, "pattern": "^[A-Z]{3}$", "type": "string"}
order|schema property type changed|PlaceOrderRequest.items: {"items": {"$ref": "#/components/schemas/LineItem"}, "minItems": 1, "type": "array"} -> {"items": {"$ref": "#/components/schemas/LineItem"}, "maxItems": 100, "minItems": 1, "type": "array"}

# Q24: "before we commit, we all know the price". Preview returns a quote
# digest -- a hash of the whole payable quote: each line's variant, quantity,
# price and discount, the delivery option and its charge, the currency, the
# total. Confirm sends it back, checkout and then order recompute it, and a
# quote that moved (a basket changed in another tab, a price or delivery price
# changed) is refused with 409 pricing-changed before anything is ordered or
# charged.
#
# * ConfirmRequest.quoteDigest REPLACES pricingVersion, which left quantity
#   and delivery out on purpose -- so both could change unseen. Required, for
#   the reason pricingVersion was: a nullable digest would let any client opt
#   out of the check. PreviewResponse.pricingVersion goes with it.
# * ConfirmRequest.deliveryOption is required: confirm charges the option the
#   shopper NAMED. It took the cheapest offered, so a K0 option would have made
#   every delivery free.
# * ConfirmRequest.destinationCountry is removed: the address's own country
#   decides where delivery is quoted for, and a self-collect order (no address)
#   is quoted for Zambia. It was already ignored whenever an address was sent.
# * PreviewResponse.appliedPromotion is removed: promotion codes are retired
#   until Phase 7's scoped promotions, which apply by themselves, and a code is
#   refused with 422 promotion-codes-not-accepted.
# * order's PlaceOrderRequest gains the same required deliveryOption and
#   quoteDigest: order prices delivery itself and checks the digest before it
#   saves anything. Its only caller is checkout's OrderClient, changed in step.

# longer declares pricingVersion or appliedPromotion (src/lib/checkout/quote.ts,

# ---------------------------------------------------------------------------
# Phase 1: a payment intent can now be CHARGING.
# ---------------------------------------------------------------------------
#
# A card is charged once per intent. From the moment the charge is started
# until its outcome is known the intent is CHARGING, and payment's reconciler
# settles one whose answer never arrived (MVP_PLAN Phase 1). That is a real
# state of the money, so both status lists gain the value.
#
# It cannot be done additively: adding an enum value is the whole change, and
# a reader with a closed list of statuses can fail on a value it does not know.
# oriah-web was checked, and it does not fail on this one, which is worse in
# its own way: AdminPaymentSchema reads status as a plain string, so a CHARGING
# row parses, shows in a fallback colour (AdminPaymentsClient) and cannot be
# filtered for, because the filter lists the four old values;
# PaymentStatusSchema, the four-value enum, is used by a test only; and
# AdminPaymentSummarySchema, a plain z.object, silently drops the new
# chargingCount. The cost is a status nobody can see or count, not a crash.
# That is recorded for the frontend stage in docs/FRONTEND_WORK.md (Phase 1,
# admin screens), with the contract tests to write first. The storefront never
# reads the intent's status: it holds only paymentIntentId (schemas/checkout.ts,
# schemas/order.ts).
#
# Reviewed and accepted 2026-11-10.
